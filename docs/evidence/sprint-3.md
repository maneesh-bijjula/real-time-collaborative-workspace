# Sprint 3: authorization, resource boundaries, and operations

Implemented from Sprint 2's `main` commit `c5fe3b2eb7c952ba616d42e1fbc5a872b589c2bd`. The sprint retains capability-link access, Yjs/Redis convergence, and exact PostgreSQL save confirmation. It adds a bounded transport ahead of Hocuspocus, staged update admission, protected telemetry, active readiness probes, structured redacted events, and validated operator alert examples.

## Scope and deployment requirements

Limits are per instance, not a distributed tenant/storage quota. The projected local document-size check does not discard accepted Redis/PostgreSQL histories; concurrent accepted peer edits can merge above that local threshold. Defaults bound admitted work but are not measured capacity guarantees. Reconnect counters are client-reported in-page rejoins, not authenticated user identity or billing data. Readiness observes dependencies and persistence at a sampling interval, not every possible future operation.

The checked-in Compose topology is a localhost verification/development setup. A public deployment still needs HTTPS/WSS, private backend networks, strong independent credentials, exact origins, correctly restricted/overwriting trusted proxies, an edge quota if needed, per-node scraping, and configured alert destinations. These controls and their limits are documented; no blanket security certification, independent penetration test, or arbitrary-load availability claim is made.

Local runs use only disposable Sprint 3 test services/databases and the disposable four-container verification topology. Ordinary application data/volumes, Project 1, CloudDrive, and the resume are preserved. The work is delivered directly on `main`, without a feature branch or pull request.

The 50-editor workload, <100 ms p95 propagation, and <2-second reconnect targets remain unverified pending Sprint 4. Full backup restoration and release closure remain Sprint 5.
